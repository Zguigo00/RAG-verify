## 一、定位与设计原则

**场景**：多人/多队各自实现一套 RAG，要在同一套考卷上比出谁更好，并且能解释**差在哪一环**。

三条设计原则决定了后面所有取舍：

| 原则 | 后果 |
|---|---|
| **不侵入被测系统** | 只认一份「答题卡」JSONL。谁用 LangChain / LlamaIndex / Java / 自研都行，横向可比 |
| **不给单一总分** | 分层指标 + Pareto，权重交给评委（不同业务权重不同：法律重引用、客服重延迟） |
| **评测要能指导优化** | 答错的题归因到「该改 Embedding 还是 Reranker 还是 Prompt」 |

第三条是差异点。市面上很多工具只给 `Accuracy = 87%`，而这个会给：

```
Retrieval Recall 94%  但 Context Precision 61%
  → 召回不错但噪声多
  → 进一步发现 Top20→Top5 的 reranker 效果不好
  → 优化后 Faithfulness 87% → 94%，Answer Correctness 85% → 91%
```

**核心价值主张**：不是打分，是诊断。

## 二、整体数据流

```
                          【主办方持有】
              dataset_v1.jsonl（50 题，含标准答案）
              corpus/chunks.jsonl（114 个官方 chunk）
              prompts/（6 份评分细则）
                          │
        ┌─────────────────┼─────────────────┐
        ↓                 ↓                 ↓
   make-public        pack             （保留暗题）
   剥离泄题字段      打工具箱 zip
        │                 │
        └────────┬────────┘
                 ↓
        dist/rag-bench-kit.zip ──── 发给参赛方
                 │
                 ↓
   【参赛方】用任何语言跑自己的 RAG
        产出 run_log.jsonl（答题卡）
                 │
                 ↓
        validate ── schema + 跨行一致性 + chunk_id 真伪 + 覆盖率
                 │
        ┌────────┼─────────┐
        ↓        ↓         ↓
      run      judge      audit
   （确定性）（LLM Judge）（反作弊）
        │        │         │
        └────────┴─────────┘
                 ↓
        results/*.json ──→ report（单文件 HTML）
                 │
                 ↓
        Scorecard / 错误归因 / Pareto / 题型·行业雷达图
```

**关键**：参赛方永远接触不到 `dataset_v1.jsonl` 的 `ground_truth_*`。这是横向可比的前提。

## 三、一次评测的生命周期

| # | 阶段 | 命令 | 产出 |
|---|---|---|---|
| 1 | 备卷 | `pack --dataset dataset/dataset_v1.jsonl` | `dist/rag-bench-kit.zip`（38 文件） |
| 2 | 发卷 | 把 zip 发出去 | 参赛方拿到公开考卷 + chunk 库 + 模板 + 校验器 |
| 3 | 交卷 | 参赛方跑自己的 RAG | `run_log.jsonl` |
| 4 | 收卷 | `validate` | 0 错误才收；覆盖率报告 |

## 四、六大模块

### ① 数据契约 `schemas/` —— 4 份 JSON Schema

| 文件 | 谁看 | 作用 |
|---|---|---|
| `dataset.schema.json` | 主办方 | 完整考卷（含标准答案） |
| `dataset_public.schema.json` | 参赛方 | 公开考卷，只有 `question_id` / `question` / `domain` |
| `run_log.schema.json` | 双方 | 答题卡 |
| `human_labels.schema.json` | 标注员 | 人工复核，用于校准 LLM Judge |

**为什么用 JSON Schema 而不是 Python 校验**：公开标准，各语言都有实现（Java/Node 也能跑），IDE 还能给参赛方补全提示。

**schema 的能力边界**（决定了为什么还要 Python 语义层）：

| schema 能查 | schema 查不了 |
|---|---|
| 字段存在性、类型、取值范围 | 题号跨行唯一 |
| 枚举（如 category） | 一文件一 system_name |
| 字符串 pattern | `rank` 从 1 开始连续不重复 |
| `if/then` 条件（如无答案题不得有 gt chunks） | 跨文件外键（chunk_id 真伪） |
| | 覆盖率统计 |

### ② 校验器 `rag_eval/validate.py`（406 行，最大模块）

```
load_jsonl()      解析层   JSONL → [(行号, 记录)]
schema_errors()   结构层   jsonschema 逐条，错误指到字段路径
check_*()         语义层   跨行/跨文件一致性
check_chunk_ids() 真伪层   chunk_id 是否官方编号 + text 是否原文
coverage_report() 覆盖率   决定能算哪些指标
```

**错误信息设计**（重点）：

```
run_log.jsonl:5  字段 `retrieved_chunks/0/rank`: 0 is less than the minimum of 1
```

JSONL 一行一条，人眼定位痛苦。带 `文件:行号 字段路径` 就能直接跳过去改。

**职责划分**：`errors` 非空才 exit 1（拒收），`warnings` 只提示（收下，评测时扣分）。
「无答案题却作答」只给警告 —— 它是合法提交，我们就是要测他会不会幻觉。
**校验器只管格式，评测器才管对错。**

### ③ 指标引擎 `retrieval.py`(133) + `system.py`(80) + `aggregate.py`(168)

**检索层**（纯公式）：`Hit@K` / `Recall@K` / `Precision@K` / `MRR@K` / `NDCG@K`，K∈{1,3,5,10}

> 术语澄清：`检测RAG质量.md` §14 的「Recall@K = 成功找到的问题数/总问题数」其实是 IR 的
> **Hit@K**。两个都实现了 —— 多跳题要看 chunk 级 `Recall@K`（3 个证据只找到 1 个会现形）。

NDCG 用 `2^rel - 1` 增益（relevance 0-3 → 0/1/3/7），IDCG 取 gt relevance 降序的理想排序。

**三个防博弈设计**：

| 设计 | 堵的漏洞 |
|---|---|
| `Precision` 分母固定取 K | 只返回 2 条也算 2/5，堵「少返回少扣分」 |
| 无答案题 / 缺字段 / 超时返回 `None` | 不计 0 分，不拉低均值 |
| `mean_dict` 跳过 `None` | 缺字段不扣分 |

**`aggregate.py`**：按题型 + 按行业分组（§44「不要只测平均值」）、Pareto 前沿（§57 三目标支配，不做加权总分）。

### ④ 错误归因 `rag_eval/triage.py`（262 行，差异化亮点）

按 §53 的 Step 1→5 短路决策树：

```
error 非空                          → System Error     → 工程稳定性
├─ 无答案题未拒答                    → No-answer Error  → 拒答策略（幻觉）
├─ 有答案却拒答                      → No-answer Error  → 拒答策略（误拒）
└─ 答错？
   ├─ gt chunk 不在 retrieved       → Retrieval Error  → Embedding / BM25 / Hybrid
   ├─ 在 retrieved 但没进 context    → Ranking Error    → Reranker / Top-K
   ├─ 该进 context 却缺失/截断       → Context Error    → Chunking / 上下文组装
   ├─ 证据齐全但引了非 gt 的 chunk   → Citation Error   → 引用生成 / 时间消歧
   ├─ 证据齐全却答错                 → Generation Error → Prompt / LLM
   └─ 答对但引用错                   → Citation Error
```

**最容易写错的分支**（有专门测试）：正确证据已进 context 却答错，且引用指向旧版本 chunk
→ 归因为 **Citation Error 而非 Generation Error**。因为该改的是版本消歧，不是 Prompt。

每条归因附 `advice` 字段，直接映射到「建议优化哪个组件」。

### ⑤ LLM Judge `judge.py`(166) + `judge_metrics.py`(108) + `calibration.py`(111)

- **OpenAI 兼容协议**（DeepSeek / Qwen / vLLM / Ollama 都能接），纯标准库 `urllib`，零新增依赖
- 温度 0 + `response_format: json_object` + 容错抠 JSON + 指数退避重试
- **3 次取中位分**，保留 `spread`（≥2 标记「不稳，建议人工复核」）
- `prompts/` 6 份评分细则，一指标一文件，改 rubric 不动代码

**κ 校准是必须的**（§50）：全判 1 的 judge 一致率 0.60 但 **κ = 0.0**
—— 裸一致率会被类别不平衡骗过。`calibrate` 在 κ < 0.6 时 exit 1，可当 CI 闸门。

**判定来源优先级**：`LLM Judge > 人工标注 > 规则 approx_correct`
`results.json` 的 `judge` 字段如实标注本次用了哪种，不冒充。

### ⑥ 发卷与防作弊 `pack.py`(234) + `audit.py`(143)

**泄题防护**：公开版只留 3 个字段。容易漏的四项 —

| 字段 | 泄露程度 |
|---|---|
| `expected_abstain` | 等于告诉对方「这题该拒答」，Abstention 指标直接失效 |
| `category` | `no_answer` / `temporal` / `multi_hop` 全是检索策略提示 |
| `difficulty` | `hard` = 提示这题有坑 |
| `notes` | 出题备注，含设计意图 |

发卷前两道闸：字段名黑名单 + 标准答案原文子串扫描，命中即拦截。

**`audit` 一致性审计**：真跑的中间过程会留下物理约束痕迹，伪造的留不下。
且这些约束**不需要知道标准答案**就能验证：

| 级别 | 信号 | 物理依据 |
|---|---|---|
| high | `token_context_mismatch` | context 840 字符却 20 token（42 字/词元）→ 任何 tokenizer 都做不到 |
| high | `score_constant` | 多个 chunk 的 score 全同 → 真实检索是连续分布 |
| high | `latency_impossible` | 5000 token 却 3ms |
| high | `latency_degenerate` | 全场 latency 只有 1-2 个取值 |
| medium | `trace_over_total` | 分阶段耗时之和 > 端到端耗时 |
| medium | `claim_not_in_answer` | 引用的 claim 不在答案原文 → 事后倒着配的 |
| low | `context_understated` | input_tokens 远超 context 字符数（**已留 2000 字符 prompt 模板余量**；模板较长属正常解释） |
| low | `score_rank_inconsistent` | score 随 rank 上升（reranker 情况下属正常） |

实测：真实 baseline **零误报**，伪造答卷判 high。

**暗题 `--hold-out`**：按题型分层抽样，**每类至少 1 题**
（少了这层保底，小题型如 hard/long/ambiguous 拿不到暗题，按题型硬编码照样过）。

## 五、八个关键设计决策

这些是**从代码里读不出来的「为什么」**，也是最容易被后人改坏的地方。

### 1. 为什么用文件而不是 API

各队技术栈不同（Python/Java/自研），逼他们继承基类等于逼他们改架构。
文件是最低公分母，且**可存档、可 diff、可审计** —— 防作弊要的就是可审计。

### 2. 为什么缺字段是 N/A 不是 0 分

否则最优策略是**只交 `answer`**：检索层不交就不扣分，反而比交了但检索差的队分数高。
用「覆盖率报告 + N/A 标注」把这个博弈漏洞堵住。

### 3. 为什么 chunk 切法必须固定

`ground_truth_chunks` 按官方编号标注。自切会导致 chunk_id 对不上，检索层指标全算不出来。

| 可自由调整 | 必须固定 |
|---|---|
| Embedding / BM25 / Hybrid / Reranker / Top-K / Query Rewrite / Prompt / LLM | chunk 切法（每个 `## ` 小节 = 1 个 chunk） |

想测自己的切分策略是另一场独立实验，不计入本场比试。

### 4. 为什么公开版要剥 `category`

它和 `expected_abstain` 一样泄题：

```
category: "no_answer"  →  对方写 if category == "no_answer": return 拒答
                          Abstention Accuracy 直接满分，指标完全失效
category: "temporal"   →  提示去查版本
category: "multi_hop"  →  提示调大 Top-K
```

改由**评测报告**给题型拆分（Scorecard + 题型雷达图）。想让参赛方自查，
可在收官后用 `reveal-categories` 命令事后公开（已实现，含 difficulty/expected_abstain，ground_truth 仍不发）。

### 5. 为什么不给总分

法律 RAG 重引用与 Faithfulness、客服重 Relevance 与 Latency、医疗重拒答与正确性。
用 Pareto（质量↑ 延迟↓ 成本↓ 三目标支配关系）+ 可调权重滑块，把「好」的定义交给评委。

### 6. 为什么用 Cohen's κ 而不是一致率

全判 1 的 judge 一致率 0.60 但 κ = 0.0 —— 类别不平衡时裸一致率会骗人。
κ < 0.6 拒绝放量，改 rubric 重测。

### 7. 为什么暗题要每类至少 1 题

纯按比例分配时，`hard(2题)` / `long(4)` / `ambiguous(4)` 会拿不到暗题
（`10 × 2/50 = 0`）。这正好漏掉「按题型硬编码」这个面。所以必须保底每类 1 题。

### 8. 为什么 audit 输出叫「可疑信号」不叫「作弊」

每条信号都有正常解释（如 rank 由 reranker 决定而 score 是向量相似度，排序不一致属正常）。
**冤枉一个诚实队伍的代价比放过一个作弊的更大。** 输出明确定位为「需人工复核」。

## 七、数据契约速查

### 答题卡 `run_log.jsonl`（每题一行）

必填 3 个：`system_name` / `question_id` / `answer`

| 可选字段 | 缺了影响 |
|---|---|
| `retrieved_chunks[]`（含 `chunk_id`/`rank`/`score`/`text`） | 评不了 Recall@K / MRR / NDCG |
| `context` | 评不了 Faithfulness / Context 系列 |
| `citations[]`（`claim` + `chunk_id`） | 评不了 Citation 系列 |
| `latency_ms` / `input_tokens` / `output_tokens` / `cost_usd` | 评不了 P95 / cost / Pareto |
| `abstained` | 拒答判定退回规则推断 |
| `query_rewritten` / `trace` / `debug` | 不算分，用于 debug |
| `error` | 非空表示本题失败，计 error rate |

**可选字段允许显式填 `null`**（真实代码序列化常输出 null），与缺字段等价。
**顶层禁止未知字段**（`additionalProperties: false`）—— 防拼错字段名导致指标静默丢失。
自定义字段一律放 `debug`。

### 官方 chunk 编号

`chunk_id = <doc_id>__<NNN>`，每个 `## ` 小节一个 chunk，编号可复现。
对照表 `corpus/chunk_index.json`（chunk_id → 文档文件 + 行号范围）。
生成：`python corpus/build_corpus.py`

### 测试集

`dataset_v1.jsonl` 每条含：`question_id` / `question` / `domain` / `category` / `difficulty`
/ `ground_truth_answer` / `ground_truth_chunks`（含 0-3 分级 relevance）/ `ground_truth_facts` / `expected_abstain`

题型 8 类：`simple` / `multi_hop` / `long` / `temporal` / `multi_doc` / `no_answer` / `ambiguous` / `hard`
行业维度 `domain` 与题型正交，`corpus/domains.json` 注册（10 个行业：2 active + 8 planned）

### 已知局限

1. **演示语料的分数不能比真人** —— 语料是虚构的（上海云启科技 / 云启商城），数字是编造值
   刻意让 LLM 参数知识失效，只能靠检索答对。要真比须换真实物料重出考卷。
2. **文件提交弱防作弊** —— audit 只能提高作弊成本，无法根除。
   彻底解决只有方式 B：主办方持题统一调 `POST /ask`，chunks/context/latency 由我方记录。
3. **规则版 `approx_correct` 是过渡** —— 用「标准答案里的数字是否都出现在回答里」做锚定，
   抓版本混淆有效但抓不到语义等价 / 漏答。生产使用请跑 Judge 并做 κ 校准。
4. **chunk 切法固定** —— 测自己的切分策略是另一场实验。

## 十、开发地图

### 近期（建议顺序）

| 优先级 | 事项 | 说明 |
|---|---|---|
| P0 | **方式 B（HTTP 代跑）** | `POST /ask` 规范 + 代跑器 + 统一计时。做完防作弊就有一条不依赖诚信的技术路径 |
| P1 | **交互式 Dashboard** | `report` 已出静态六视图；交互版补权重滑块 / 逐题下钻 / Judge 一致性页 |
| P2 | **补行业** | 每行业：注册 `domains.json` → 建 `corpus/<domain>/` → `build_corpus.py` → 出题 → 合并 |
| P3 | **换真实语料** | 有了真实物料就重出考卷，pipeline 直接复用 |

### 补一个新行业的 5 步（不改代码）

1. `corpus/domains.json` 注册行业，`status` 置 `active`
2. 建 `corpus/<domain>/`，放 `.md` 语料（`## ` 小节切分）
3. `python corpus/build_corpus.py` 重新生成 chunk 库与对照表
4. 建 `dataset/domains/<domain>.jsonl`，按 8 种题型出题
5. 合并各行业 → 新的 `dataset_v1.jsonl` → 跑 `validate`

### 改评分细则的注意事项

`prompts/<metric>.md` 直接改，三处要看：评分档位描述、**「特别注意」里的误判防护**
（如「版本混淆算噪声」「限定词丢失扣档」）、输出 JSON 契约（不要动）。
**改完必须重跑 `calibrate`**，κ < 0.6 说明改坏了。
